# 开发规则

## 对话风格

- 回答保持简短精炼
- 提交（commit）、issue、PR 评论和代码中不使用表情符号
- 不使用空洞或客气的填充文字（例如写 "Thanks @user" 而不是 "Thanks so much @user!"）
- 只使用技术性的文字表述，直接了当
- 使用简洁、清晰、简单的语言。使用不可避免的术语前先给出定义
- 解释非平凡的设计和问题时，按"问题、具体示例或简短调用轨迹、然后解决方案"的结构来组织。说明为什么该解决方案是必要的，并将其与可选的复杂度区分开
- 优先使用具体行为和简短示例，而不是抽象总结、密集术语或无解释的变更列表
- 当用户提问时，先回答问题，再进行编辑或运行实现命令
- 回应用户反馈或分析时，先明确表示同意还是不同意，再说明你改了什么

## 代码质量

- 在进行大范围修改、编辑尚未完整检查过的文件、或被要求调查/审计之前，先完整阅读文件。不要依赖搜索片段来做大范围修改
- 除非绝对必要，不使用 `any`
- 只有一个调用点的单行辅助函数直接内联
- 查看 node_modules 中的外部 API 类型；不要靠猜
- **禁止内联导入**（`await import()`、`import("pkg").Type`、动态类型导入）。只允许顶层导入
- 绝不为了修复过期依赖导致的类型错误而删除或降级代码；应该升级依赖
- 在根配置检查的代码（`packages/*/src`、`packages/*/test`、`packages/coding-agent/examples`）中只使用可擦除的 TypeScript 语法（Node strip-only 模式）：不使用参数属性、`enum`、`namespace`/`module`、`import =`、`export =` 或其他需要 JS 产物的构造。使用显式字段加构造函数赋值
- 在移除看起来是有意设计的功能或代码之前，务必先询问
- 除非用户要求，不保留向后兼容
- 绝不硬编码按键检查（例如 `matchesKey(keyData, "ctrl+x")`）。将默认值添加到 `DEFAULT_EDITOR_KEYBINDINGS` 或 `DEFAULT_APP_KEYBINDINGS`，使其保持可配置
- 绝不直接修改 `packages/ai/src/models.generated.ts`；改为更新 `packages/ai/scripts/generate-models.ts` 然后重新生成。包含生成的 `models.generated.ts` 差异始终是可以的，即使重新生成时包含了无关的上游模型元数据变更

## 命令

- 代码变更后（文档除外）：运行 `npm run check`（完整输出，不截断）。提交前修复所有错误、警告和信息提示。它不运行测试
- 除非用户要求，绝不运行 `npm run build` 或 `npm test`
- 绝不直接运行完整的 vitest 套件：它包含在存在 endpoint/auth 环境变量时会激活的 e2e 测试。所有非 e2e 测试从仓库根目录运行 `./test.sh`。否则从包根目录运行指定测试：
  - Vitest：`node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run test/specific.test.ts`
  - `packages/tui`（`node:test`）：`node --test test/specific.test.ts`
- 如果你创建或修改了测试文件，运行它并迭代测试或实现直到通过
- 对于 `packages/coding-agent/test/suite/`，使用 `test/suite/harness.ts` 加上 faux provider。不使用真实 provider API、密钥或付费 token
- 为修复 github issue 编写回归测试时，在测试旁边添加带 github issue 编号的注释
- 临时脚本请 `write` 到临时文件（例如 `/tmp`），运行，必要时编辑，完成后删除。不要在 `bash` 命令中嵌入多行脚本
- 除非用户要求，绝不提交

## 依赖与安装安全

- 将 npm 依赖和 lockfile 变更视为经过审查的代码。直接外部依赖保持固定到精确版本
- 更新 `undici` 时，你必须阅读目标版本的 changelog/release notes，并在应用更新前评估是否有变更可能影响功能
- 本地安装/更新使用 `npm install --ignore-scripts`；干净/CI 风格安装使用 `npm ci --ignore-scripts`。除非用户要求，不运行生命周期脚本
- 如果依赖元数据变更，用 `npm install --package-lock-only --ignore-scripts` 刷新 `package-lock.json`
- 如果 `packages/coding-agent/npm-shrinkwrap.json` 需要重新生成，运行 `node scripts/generate-coding-agent-shrinkwrap.mjs`（用 `--check` 或 `npm run check` 验证）。带生命周期脚本的新依赖需要审查并在该脚本中显式添加白名单条目；绝不静默添加
- 除非设置 `PI_ALLOW_LOCKFILE_CHANGE=1`，pre-commit 会阻止 lockfile 提交。除非用户希望提交 lockfile 变更，否则不要绕过

## Git

多个 pi 会话可能同时在此 cwd 中运行，各自修改不同的文件。触及你自己变更之外的未暂存、已暂存或未跟踪文件的 Git 操作会破坏其他会话的工作。遵循以下规则：

提交：

- 只提交你本次会话中修改的文件
- 显式暂存路径（`git add <path1> <path2>`）；绝不使用 `git add -A` / `git add .`
- 提交前运行 `git status`，确认只暂存了你的文件
- `packages/ai/src/models.generated.ts` 始终可以与你的文件一起包含
- 消息格式：`{feat,fix,docs}[(ai,tui,agent,coding-agent)]: <提交消息>（可选多行）`。消息要信息丰富且简洁

绝不运行（会破坏其他 agent 的工作或绕过检查）：

- `git reset --hard`、`git checkout .`、`git clean -fd`、`git stash`、`git add -A`、`git add .`、`git commit --no-verify`

如果发生 rebase 冲突：

- 只在你修改过的文件中解决冲突
- 如果冲突在你未修改过的文件中，中止并询问用户
- 绝不 force push

## Issue 与 PR

贡献者门槛（自动关闭工作流、`lgtm`/`lgtmi`、质量标准）见 `CONTRIBUTING.md`。

审查 PR 时：

- 除非用户明确要求，不运行 `gh pr checkout`、`git switch` 或以其他方式将工作树切换到 PR 分支
- 使用 `gh pr view`、`gh pr diff`、`gh api` 以及对已 fetch 的 ref 使用本地 `git show`/`git diff` 来检查 PR 元数据、提交和补丁，而不切换分支
- 如果需要 PR 文件内容，fetch/读取到临时文件，或使用 `git show <ref>:<path>`，不切换分支

创建 issue 时：

- 为受影响的包添加 `pkg:*` 标签（`pkg:agent`、`pkg:ai`、`pkg:coding-agent`、`pkg:tui`）；适用的都加上

发布 issue/PR 评论时：

- 将评论写入临时文件，用 `gh issue/pr comment --body-file` 发布（绝不通过 `--body` 传递多行 markdown）
- 评论保持简洁、技术性，符合用户的语气
- 每条 AI 发布的评论末尾加上 originating prompt 指定的 AI 生成免责声明行（例如 `This comment is AI-generated by `/wr``）

通过提交关闭 issue 时：

- 在消息中包含 `fixes #<number>` 或 `closes #<number>`，这样合并时会自动关闭 issue。多个 issue 时，每个 issue 重复关键字（`closes #1, closes #2`）；共用关键字（`closes #1, #2`）只会关闭第一个

## 用 tmux 测试 pi 交互模式

在受控终端中运行 TUI（从仓库根目录）：

```bash
tmux new-session -d -s pi-test -x 80 -y 24
tmux send-keys -t pi-test "./pi-test.sh" Enter
sleep 3 && tmux capture-pane -t pi-test -p     # 启动后捕获
tmux send-keys -t pi-test "your prompt here" Enter
tmux send-keys -t pi-test Escape               # 特殊键（C-o 表示 ctrl+o 等）
tmux kill-session -t pi-test
```

## Changelog

位置：`packages/*/CHANGELOG.md`（每个包一个）。

`## [Unreleased]` 下的章节：`### Breaking Changes`（需要迁移的 API 变更）、`### Added`、`### Changed`、`### Fixed`、`### Removed`。

规则：

- 所有新条目放在 `## [Unreleased]` 下。先阅读完整章节再追加到已有小节；绝不重复创建小节
- 已发布的版本章节（例如 `## [0.12.2]`）不可变；绝不修改
- 在 `main` 以外的分支或 pull request 上工作时，不创建 changelog 条目

署名：

- 内部（来自 issue）：`Fixed foo bar ([#123](https://github.com/earendil-works/pi-mono/issues/123))`
- 外部贡献：`Added feature X ([#456](https://github.com/earendil-works/pi-mono/pull/456) by [@username](https://github.com/username))`

## 发布

**锁步版本（Lockstep versioning）**：所有包共享一个版本；每次发布一起更新。`patch` = 修复 + 新增，`minor` = 破坏性变更。不进行 major 发布。

1. **更新 CHANGELOG**：询问用户是否在 `main` 的最新提交上运行过 `/cl` prompt。如果没有，必须先运行 `/cl` 审计并更新每个包的 `[Unreleased]` 章节再发布

2. **本地冒烟测试**：构建一个未发布的版本，并从仓库外部冒烟测试（这样它无法解析 workspace 文件）：
   ```bash
   npm run release:local -- --out /tmp/pi-local-release --force
   cd /tmp

   # Node 包安装冒烟测试
   /tmp/pi-local-release/node/pi --help
   /tmp/pi-local-release/node/pi --version
   /tmp/pi-local-release/node/pi --list-models
   /tmp/pi-local-release/node/pi -p "Say exactly: ok"
   /tmp/pi-local-release/node/pi

   # Bun 二进制冒烟测试
   /tmp/pi-local-release/bun/pi --help
   /tmp/pi-local-release/bun/pi --version
   /tmp/pi-local-release/bun/pi --list-models
   /tmp/pi-local-release/bun/pi -p "Say exactly: ok"
   /tmp/pi-local-release/bun/pi
   ```
   验证 Node 和 Bun 的启动、模型/账户列表、交互式启动，以及至少一个使用预期默认 provider 的真实 prompt。裸命令 `/tmp/pi-local-release/node/pi` 和 `/tmp/pi-local-release/bun/pi` 启动交互模式；在 tmux 中运行每一个，提交一个 prompt，并等待模型回复后才算交互式冒烟测试通过。失败是发布阻断项，除非用户明确接受风险

3. **运行发布脚本**：
   ```bash
   PI_ALLOW_LOCKFILE_CHANGE=1 npm_config_min_release_age=0 npm run release:patch    # 修复 + 新增
   PI_ALLOW_LOCKFILE_CHANGE=1 npm_config_min_release_age=0 npm run release:minor    # 破坏性变更
   ```
   `npm_config_min_release_age=0` 只用于发布命令。否则仓库正常的 npm 年龄门禁可能会在当前 workspace 包版本最近刚发布时阻止发布时的 lockfile 刷新。push 之前审查发布产生的任何 lockfile 或 shrinkwrap 差异

   发布脚本会提升所有包版本、更新 changelog、重新生成发布产物、运行 `npm run check`、提交 `Release vX.Y.Z`、打标签 `vX.Y.Z`、添加全新的 `## [Unreleased]` changelog 章节、提交 `Add [Unreleased] section for next cycle`，然后 push `main` 和标签。标签 push 后不要重新运行发布脚本

4. **CI 验证并宣布 npm 发布**：push `vX.Y.Z` 标签会触发 `.github/workflows/build-binaries.yml`。`publish-npm` job 通过 GitHub Actions OIDC 使用 npm trusted publishing，环境为 `npm-publish`；不需要本地 `npm publish`、`npm whoami`、OTP 或 WebAuthn 流程。发布后，`announce-pi-dev-release` 验证每个公开的 workspace 包在精确的发布版本上可解析且其 npm tarball 可用，然后将验证过的发布标记写入 R2。`pi.dev/api/latest-version` 读取该标记；在此 job 成功之前绝不能从 npm 宣布发布

5. **如果 CI 发布或宣布失败**：检查失败的 job。发布助手是幂等的，会跳过 npm 上已存在的包版本；宣布 job 在更新 R2 标记前会重新检查可用性。修复 CI 或临时 npm 问题后重新运行失败的 job 或 workflow。不要为同一版本重新运行 `npm run release:patch` 或 `npm run release:minor`

如果用户的指令与本文档中的任何规则冲突，覆盖前先请求明确确认。只有那时才执行他们的指令。
