# 系统提示词变化的处理实践：替换 vs 追加（以发给模型的上下文为主）

状态：草稿（2026-09-19 整理；本文是业界实践层面的对照认知，非 pi 源码事实，非某具体框架某版本的源码级结论——如需精确到某框架请另查其源码/文档）

## 它是什么（≤5 句）

一般 Agent 工具处理「系统提示词变化」（典型场景：session 中途切换智能体/角色）时，发给大模型的上下文用**整体替换**：新提示词替换老提示词放在开头，老提示词直接消失，不追加、不并存。系统提示词在 API 层是独立字段（OpenAI 的 `messages[0]`、Anthropic 的 `system` 字段），语义是「当前角色定义」，换角色 = 换字段值。追加的写法（保留老的 + 后面告知变化）会带来语义混乱、token 浪费，且缓存照旧失效，故无人采用。

## 主流实践三类

| 类型 | 代表 | 变化方式 | 落盘 |
|---|---|---|---|
| 内存态 + 整体替换 | LangChain / LangGraph、LlamaIndex、Aider、OpenHands | 内存字符串赋新值，每次请求拼 `[当前 system, ...历史]` | 不落盘，无历史 |
| 服务端字段替换 | OpenAI Assistants API | `instructions` 字段整体替换，只有当前值 | 服务端存当前值，无历史版本 |
| 独立 system 字段 + 对话内追加 | Anthropic 生态（Claude Code 等） | 主体替换 `system` 字段；「增量补充」可用 mid-conversation system 块 | 以 provider 为准 |

注意第三种里的「对话内追加」是**增量补充**（如「后续请用中文」），不是**换角色**；切智能体属于换角色，仍走替换。

## 为什么「追加」不成立

如果「开头保留 A、后面追加 B 告知变化」，同时踩三个坑：

1. **语义混乱**：模型看到两份角色指令，需自行判断哪份生效。
2. **token 浪费**：A 已失效仍占上下文位置，每次请求白付这部分 token。
3. **缓存照旧失效**：前缀毕竟变了，KV cache 该失效还失效，没省任何东西。

所以「追加告知变化」工程上无收益反而有害。

## 以 KV cache / token / 费用为视角

- **替换是唯一合理选择**：发给模型永远是「一份当前提示词 + 历史」，token 量 = `|当前提示词| + |历史|`，不因切换次数累积。
- **切提示词的固有代价**：前缀从第 0 个 token 变 → 前缀缓存失效 → 该次请求重新计算 KV（`cache write`，贵）→ 费用上升。这是「换角色」的语义需求决定的，躲不掉。
- **贵是一次性的**：切换**那一次**请求失效重算，之后前缀稳定、缓存恢复命中。参照物是「不切、一直追加对话」（前缀不变、全命中、最便宜）。
- **失效范围看 provider**：有显式断点缓存（Anthropic 系）只丢系统提示词段；只有自动前缀缓存（OpenAI 原生）则整个前缀全失效。

## 与 pi 的对照

pi 的「持久态 + 结构化 sections + 按段 diff 追加」是少数派，但**落在「发给模型」这一步时，pi 通过重放收敛到和主流一样的结果——替换**：

| 维度 | 主流（内存态整体替换） | pi（持久态按段 patch） |
|---|---|---|
| 落盘 | 不落盘，无历史 | JSONL 落盘，可追溯 |
| 发给模型的上下文 | 一份当前提示词（替换） | 重放后一份当前提示词（替换） |
| token / 费用 | 不因切换累积 | 不因切换累积（重放覆盖） |
| 切提示词的缓存代价 | 前缀失效 | 前缀失效（靠断点压缩失效范围） |

**结论**：pi 多付的钱是「存储」和「工程复杂度」，不是「推理 token」；主流省下「存储」，代价是「会话不自洽、无法精确追溯提示词」。两者在「发给模型」这一层殊途同归。
