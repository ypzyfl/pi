# 贡献指南（pi）

本指南的存在是为了节省双方的时间。

## 理念

先说最重要的一点：**pi 的核心是极简的**。

如果你的功能不属于核心，它就应该做成一个扩展。让核心膨胀的 PR 很可能被拒绝。

pi 的核心的存在就是为了保持极简且可扩展，从而能够被扩展影响和操控。不过，即使是给扩展用的钩子点（hook point）也应经过充分思考和讨论，以避免添加难以维护的膨胀和复杂的交互。

## 唯一规则

**你必须理解你的代码。** 如果你无法解释你的变更做了什么、以及它们如何与系统其余部分交互，你的 PR 将被关闭。

用 AI 写代码没问题。不理解内容就提交 AI 生成的垃圾（slop）则不行。

如果你使用 agent，请从 `pi` 根目录运行它，以便它自动加载 `AGENTS.md`。你的 agent 必须遵守该文件中的规则和指南。

## 贡献门槛

来自新贡献者的所有 issue 和 PR 默认会被自动关闭。

周五至周日提交的 issue 不保证会被审查。如果有紧急事项，请在 Discord 上询问：https://discord.com/invite/3cU7Bz4UPx

维护者每天审查被自动关闭的 issue，并重新打开有价值的那些。不满足下述质量标准的 issue 不会被重新打开，也不会收到回复。

通过维护者在 issue 上的回复实现批准：

- `lgtmi`：你今后的 issue 不会被自动关闭
- `lgtm`：你今后的 issue 和 PR 都不会被自动关闭

该命令必须位于回复的开头（可选地跟在一个或多个 `@username` 提及之后）或结尾。`lgtmi` 不授予提交 PR 的权利。只有 `lgtm` 授予提交 PR 的权利。

## issue 的质量标准

如果你要开 issue，必须使用两个 GitHub issue 模板之一。

如果你要开 issue，请保持简短、具体、值得阅读。

- 保持简洁。如果一屏放不下，就太长了。
- 用自己的语言写（不要用 LLM 生成文本；如果非用不可，请跟一条明确标注 AI 生成的评论）。
- 清楚地陈述 bug 或请求。
- 说明它为什么重要。
- 如果你想自己实现这个变更，请说明。

如果 issue 属实且写得好，维护者可能会重新打开它，或按上述命令位置回复 `lgtmi` 或 `lgtm`。

## 封禁

如果你两次无视本文档，或用 agent 生成的 issue 刷屏 issue 追踪器，你的 GitHub 账户将被永久封禁。

如果你通过自动化发送大量 issue，你的 GitHub 账户将被永久封禁。概不反悔。

## 提交 PR 之前

除非你已获得维护者以上述命令位置的 `lgtm` 批准，否则不要开 PR。

提交 PR 之前：

```bash
npm run check
./test.sh
```

两者都必须通过。

不要编辑 `CHANGELOG.md`。Changelog 条目由维护者添加。

如果你要向 `packages/ai` 添加新 provider，请查看 `AGENTS.md` 了解必需的测试。

## 常见问题

### 为什么新 issue 和 PR 会被自动关闭？

pi 收到的 issue 数量超出了维护者能够负责任地实时审查的范围。许多报告不满足本指南的质量标准或不遵循 CONTRIBUTING.md，有些是经 agent 不加思考地甩到仓库的，而不是由提交者本人审阅和打磨过的。自动关闭创建了一个缓冲区，让维护者可以按自己的节奏审查 issue 追踪器，并重新打开满足质量标准的 issue。

### 为什么周末的 issue 优先级更低？

我们在工作时间内对 issue 追踪器做分诊。这意味着周末会积累更多 issue。周五至周日提交的任何内容，都可能在周一的审查队列中被遗漏或给予较低优先级。如果问题紧急，请在 Discord 上提问，并附上简短说明、复现步骤和相关日志。

### 为什么有些 issue 得不到回复？

回复本身也是维护工作。低信号 issue、含混不清的报告、重复项以及不遵循本指南的 issue，可能不经讨论就被关闭。这为可复现的 bug、深思熟虑的请求，以及做了功课让报告可执行的贡献者留出了时间。

### 为什么不让 AI 分诊一切？

AI 可以帮忙归类重复项、总结报告、发现缺失信息。但做最终的维护者决策不交给它。打磨得再漂亮的 AI 生成 issue 仍可能是错的、有误导性的，或调查起来代价高昂。人工审查仍是最后的关卡。

### 这对贡献者有敌意吗？

没有。这是防止维护者倦怠和 issue 追踪器刷屏的护栏。简短、具体、可复现的 issue 受欢迎，深思熟虑的贡献受欢迎。自动化垃圾、理所当然的索取态度和大量低努力报告则不受欢迎。
